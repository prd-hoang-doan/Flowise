# Skill V2 — Test Prompts & Expected Behaviour

Use these prompts inside a chatflow / agentflow that has the
**Skill** tool node wired up and pointed at the `Recruiting` skill
from `./recruiting/`. See [`README.md`](./README.md) for setup.

Every prompt block below is a complete copy-paste. Comments after
`→` describe what the agent should do if the Skill V2 bundle is
compiled correctly.

---

## 0. Smoke test

```
What tools do you have available? Briefly describe each one.
```

→ The agent should list (at minimum) `resume_screener`,
`interview_questions`, and `email_drafter` (if all three markdown
files were selected on the Skill tool node). Each description comes
from the first `#` heading + the compiler's appended dependency
hint.

When a sandbox is available, the agent should also see
`bash_<SkillName>` (e.g. `bash_Recruiting`) whose description carries
a **Suggested invocations** cheat-sheet grouped by file type — JS,
Python, shell, and text files, each with a `node …`, `python3 …`,
`bash …`, or `cat …` template. The per-skill tools' responses
additionally append an **Execution helpers** section mapping each
referenced file to the exact bash command.

## 1. Resume screening — sandbox execution happy path

```
Please screen this candidate for the Senior Python Developer role.

Candidate resume:
------------------
Jane Doe — 8 years of professional Python, 4 years on AWS EKS.
Built Kafka-based ingestion pipelines processing ~300M events/day
at FinTechCo. Led a team of 3 platform engineers. Strong with
pytest, mypy, and Terraform. Minimal Snowflake exposure but deep
BigQuery experience. Active Airflow contributor. MS in CS.
```

**Expected tool-call sequence (two hops):**

1. Agent invokes `resume_screener` with `{query: "..."}`.
   → Tool returns the resolved markdown for `resume-screener.md`.
   The tail of the response contains an **Execution helpers** block
   auto-generated by the runtime:

    ```
    Execution helpers — map file references to concrete commands:
    - ./job-description.txt — read as text: call `bash_Recruiting` with {"command": "cat /home/user/skills/job-description.txt"}
    - ./scoring_algorithm.js — execute with node.js: call `bash_Recruiting` with {"command": "node /home/user/skills/scoring_algorithm.js [args...]"}
    ```

2. Agent invokes `bash_<SkillName>` using the helper line for
   `scoring_algorithm.js`, replacing `[args...]` with the resume and
   JD strings:

    ```json
    {
        "command": "node /home/user/skills/scoring_algorithm.js 'Jane Doe — 8 years of professional Python, ...' 'Senior Python Developer — Remote (EU / US)\\n\\nResponsibilities\\n...'"
    }
    ```

    → Tool returns the JSON envelope:

    ```json
    {
        "status": "ok",
        "stdout": "{\n  \"technical_fit\": 6.4,\n  \"experience_level\": 8,\n  \"culture_fit\": 7.0,\n  \"overall\": 7.1\n}",
        "stderr": "",
        "exitCode": 0,
        "durationMs": 8,
        "engine": "e2b-bash"
    }
    ```

3. Agent produces the Summary/Scores/Matches/Gaps Markdown block,
   reusing the four numeric scores from `stdout` verbatim.

**What to inspect:**

-   The chatflow trace shows **two** tool invocations in order
    (`resume_screener`, then `bash_*`).
-   `engine` is `e2b-bash` — the only execution engine the node
    supports.
-   The "Debug — scoring tool trace" section at the bottom of the
    report echoes the raw envelope — easy visual confirmation that
    the sandbox shell actually ran.
-   `exitCode` is `0` and `stderr` is empty.
-   Scores in the final Markdown table match those in `stdout`
    exactly (the skill instructs the LLM not to re-round).

## 1a. Sandbox — force a direct bash call

Use this prompt to short-circuit the LLM's judgement and trigger the
companion tool in isolation. Useful when debugging the sandbox
pipeline itself (capability detection, file materialisation,
command routing).

```
Call bash_<SkillName> with this exact command and return the raw
JSON envelope verbatim — do not summarize:

node /home/user/skills/scoring_algorithm.js '10 years Python, 6 years AWS EKS, Kafka, Snowflake, Terraform, mypy, pytest, Airflow' 'Senior Python Developer. Required: 5+ years Python, AWS, Kafka, Snowflake, Terraform, pytest.'
```

→ Agent invokes `bash_<SkillName>` directly (no `resume_screener`
hop).  
→ Envelope contains `status: "ok"`, `exitCode: 0`, and a non-empty
`stdout` with scores around **8.3 overall** (the resume lines up
closely with the JD keywords).  
→ `engine` is always `e2b-bash`.

**What to inspect:**

-   Server logs print the command line and the materialised file
    count on first invocation — verify both against the manifest.
-   The `durationMs` field is < `SKILL_V2_EXEC_TIMEOUT_MS` (15000 by
    default). If it's at or above, you either hit the clamp or the
    sandbox's own timeout.

## 1b. Sandbox — error handling (unknown path)

```
Call bash_<SkillName> with this command:
cat /home/user/skills/does_not_exist.js
```

→ Envelope returns:

```json
{
    "status": "error",
    "stdout": "",
    "stderr": "cat: /home/user/skills/does_not_exist.js: No such file or directory",
    "exitCode": 1,
    "error": { "kind": "runtime", "message": "cat: /home/user/skills/does_not_exist.js: No such file or directory" },
    "durationMs": 42,
    "engine": "e2b-bash"
}
```

→ The LLM should relay the `stderr` text verbatim instead of
hallucinating a score. The agent can recover by issuing
`ls /home/user/skills/` first to discover what actually exists.

---

## 1c. Sandbox — runtime error surfaced as envelope

Edit `scoring_algorithm.js` in the Skill workspace to include
`throw new Error('boom')` at the top, republish, then run any of the
§1 prompts.

→ Envelope is always a well-formed JSON object with
`status: "error"`, `exitCode: 1`, `error.kind: "runtime"`, and the
node stack trace in `stderr`. LangChain never sees an exception for
guest-level bugs.

**What to inspect:**

-   `error.kind` is `runtime` (node exited non-zero); it would be
    `timeout` if the process ran past the clamped budget, or
    `internal` for host/VM boot failures.

---

## 1d. Sandbox — execution disabled fallback

Two ways to exercise fallback mode:

1. **Kill-switch**: set `SKILL_V2_ALLOW_EXEC=false` in the Flowise
   env and restart.
2. **Author opt-out**: uncheck the `Enable Sandbox Shell` toggle on
   the Skill tool node. No restart needed.

Either route takes effect immediately:

→ The Skill node registers only `resume_screener` — no `bash_*`.  
→ The agent cannot run the scoring script and falls back to manual
scoring — the "Debug — scoring tool trace" section at the bottom of
the report should contain `{"engine": "unavailable"}` instead of an
envelope.

Flip the flag (or the toggle) back to re-enable the sandbox shell.

## 2. Transitive dependencies — interview plan

```
Now generate an interview plan for Jane Doe based on the screening
you just produced.
```

→ Agent invokes `interview_questions`.  
→ The returned text contains `{{skill…}}` already resolved to the
path of `resume-screener.md` (something like `./resume-screener.md`).  
→ Agent reuses the screening from turn 1 to craft 5 behavioural +
5 technical questions, returned as a JSON code block.

**What to inspect:**

-   The bundle's `dependencyGraph[interview-questions.md]` includes
    `resume-screener.md` (direct) and any transitive tool deps.
-   The agent does not hallucinate questions for a different role.

## 3. Two-hop transitive deps — email draft

```
Draft the panel email summarising Jane Doe's screen + the interview
plan, but don't send it yet.
```

→ Agent invokes `email_drafter`.  
→ The returned text contains **two** resolved skill paths
(`./resume-screener.md` and `./interview-questions.md`) and the
`send_email` tool label.  
→ Agent produces the final email as Markdown followed by a JSON
call-plan for `send_email` — but does **not** actually call it
(because the prompt says "don't send it yet").

**What to inspect:**

-   `email-drafter.md`'s bundle entry in `bundle.json` should list
    `candidate_lookup` and `python` in its `tools.dependencies` even
    though `email-drafter.md` only declares `send_email` directly
    (that's the fixed-point transitive pass doing its job).
-   If the agent calls `send_email` anyway, you've either (a) wired
    the send_email tool into the chatflow directly (it should not be
    there — the Skill tool node does not auto-register declared
    tools in the v2 MVP; it merely advertises them in the label text)
    or (b) the agent ignored the instruction. Both outcomes are
    interesting test signals — note which one.

## 4. Placeholder-resolution edge cases

### 4a. Broken reference

Edit `resume-screener.md` in the editor, add a new placeholder that
points at a non-existent node (e.g. `{{skill.00000000-0000-0000-0000-000000000000}}`),
and try to publish.

→ Publish fails with `SKILL_V2_BROKEN_REFERENCE` and the UI surfaces
the offending node id.

### 4b. Tool group with one disabled entry

Add this block somewhere in `interview-questions.md`:

```
Preferred tool: [{{tool.sandbox.python.<uuid1>}}, {{tool.sandbox.bash.<uuid2>}}]
```

In the `Metadata` JSON, set the second entry's `enabled: false`.
Publish. The compiled artefact should contain only
`[[Python: python_<uuid1>]]` — the disabled candidate is stripped.

### 4c. Escape via code fence

Paste this into any `.md`:

```
Example of how placeholders look: `{{tool.foo.bar.baz}}`.
```

→ The inline-code span must be preserved verbatim in the compiled
output. Verify via the resolved artefact.

---

## 5. Runtime placeholders (compile-time should leave them alone)

Add a `{{question}}` somewhere inside `resume-screener.md`, e.g.:

```
The hiring manager's original framing was: {{question}}.
```

→ Publish succeeds.  
→ In the compiled `bundle.json` entry for that node, `{{question}}`
must appear **verbatim** — it is resolved at call time by
`getVariableValue` in `packages/server/src/utils/index.ts`, not at
compile time.  
→ When the agent calls the tool, the `{{question}}` is replaced
with the current user prompt.

Same verification applies to `{{$vars.*}}`, `{{$flow.*}}`,
`{{chat_history}}`, and `{{file_attachment}}`.

## 6. Bundle inspection (optional, for the curious)

```bash
# From the API pod, with DB access:
SELECT id, name, "publishedBundleId", "contentDigest"
FROM skill_v2
WHERE name = 'Recruiting';

# Then pull the bundle from object storage:
cat storage/skills-v2/<workspaceId>/<skillId>/artifacts/<bundleId>/bundle.json | jq .
```

Expected (abridged):

```json
{
    "schemaVersion": 1,
    "bundleId": "<hex>",
    "skillId": "<uuid>",
    "entries": {
        "<job-description.txt uuid>": { "kind": "data", "content": "" },
        "<scoring_algorithm.js uuid>": { "kind": "code", "content": "" },
        "<resume-screener.md uuid>": {
            "kind": "skill",
            "content": "# Resume Screening Skill\n\n…",
            "tools": {
                "dependencies": [
                    {
                        "type": "custom",
                        "provider": "hr_platform",
                        "toolName": "candidate_lookup"
                    }
                ]
            }
        },
        "<interview-questions.md uuid>": {
            "kind": "skill",
            "tools": {
                "dependencies": [
                    { "provider": "sandbox", "toolName": "python" },
                    { "provider": "hr_platform", "toolName": "candidate_lookup" }
                ]
            }
        },
        "<email-drafter.md uuid>": {
            "kind": "skill",
            "tools": {
                "dependencies": [
                    { "provider": "comms", "toolName": "send_email" },
                    { "provider": "hr_platform", "toolName": "candidate_lookup" },
                    { "provider": "sandbox", "toolName": "python" }
                ]
            }
        }
    },
    "dependencyGraph": {
        "<resume-screener.md uuid>": [],
        "<interview-questions.md uuid>": ["<resume-screener.md uuid>"],
        "<email-drafter.md uuid>": ["<resume-screener.md uuid>", "<interview-questions.md uuid>"]
    }
}
```

If your bundle looks like that, every phase of the compiler (parse,
direct compile, transitive propagation) is working end-to-end.
